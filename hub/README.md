# Hub

Центральный узел сети Smart Garden. Работает на **ESP32**. Слушает
широковещательный трафик ESP-NOW от всех периферийных устройств,
ведёт таблицу известных узлов и позволяет оператору отправлять им
команды — через Serial Monitor или через веб-интерфейс с телефона/ноута.

Подробное описание протокола, форматов сообщений и всех
задокументированных тонкостей — в [`../PROTOCOL.md`](../PROTOCOL.md).
Этот файл — про то, что конкретно делает `hub.ino` и как им пользоваться.

## Назначение

- Принимает от периферийных узлов `MSG_CONFIG` (паспорт устройства) и
  `MSG_TELEMETRY` (текущие показания), ведёт по ним таблицу устройств.
- Отправляет узлам `MSG_COMMAND` по команде оператора — из Serial или
  из браузера.
- Оповещает всю сеть о своей (пере)загрузке широковещательным
  `MSG_CONFIG` — это нужно узлам, чтобы корректно сбросить
  дедупликацию после рестарта Хаба (см. `PROTOCOL.md` §4.3).
- Раздаёт собственную Wi-Fi точку доступа с веб-страницей управления
  (см. ниже).
- Позволяет пользователю "установить" устройство через веб/Serial —
  подтверждённые устройства защищены от автоматического вытеснения и
  сохраняются в энергонезависимой памяти (NVS), переживая
  перезагрузку Хаба (см. §"Установка устройств" ниже и `PROTOCOL.md` §11).

Хаб **не занимается** доменной логикой периферии (не знает, что такое
клапан или литр) — он только маршрутизирует пакеты и разбирает payload
для отображения (см. `handleIrrigationPayload()`).

## Зависимости

- `<esp_now.h>`, `<WiFi.h>` — стандартные для arduino-esp32 3.x.
  **Важно**: API здесь заметно отличается от ESP8266 (`<espnow.h>`), в
  частности сигнатура receive-колбэка и способ регистрации пира — см.
  комментарии в начале `hub.ino`.
- `<WebServer.h>` — встроенный в ядро arduino-esp32 HTTP-сервер, без
  внешних зависимостей (ArduinoJson и т.п. не используются — JSON для
  `/api/devices` собирается вручную, ответ маленький).
- `<GardenProtocol.h>` из библиотеки `../libraries/GardenNet/` — общий
  формат пакета, дедупликация, общие MAC-константы (`BROADCAST_MAC`,
  `HUB_MAC`) и `fillPacketHeader()` (общая механика заполнения заголовка
  пакета, переиспользуемая и Хабом, и узлами). Хаб **не использует**
  класс `GardenNode` — тот написан для периферийных узлов с одним
  фиксированным адресатом (Хабом); у Хаба принципиально другая роль
  (много отправителей, произвольный адресат команды на каждый вызов,
  своя таблица устройств), поэтому вся логика маршрутизации реализована
  прямо в `hub.ino`, опираясь на общие протокольные примитивы из
  `GardenProtocol.h`, а не на класс.
- `<Preferences.h>` — встроенная в ядро arduino-esp32 обёртка над NVS
  (энергонезависимая flash-память ESP32), для хранения списка
  установленных устройств между перезагрузками.

## Как это работает

### Таблица устройств

`devices[MAX_DEVICES]` (`MAX_DEVICES=64`) двухуровневая:

- **Кандидаты** — заполняются автоматически по мере прихода
  `MSG_CONFIG`/`MSG_TELEMETRY` от новых MAC-адресов, никакой ручной
  регистрации не требуется (Plug & Play). Живут только в RAM, подлежат
  LRU-вытеснению при заполнении таблицы — подробности в `PROTOCOL.md`
  §6.2.
- **Установленные** — пользователь явно подтвердил устройство (кнопка
  "Установить" в веб-интерфейсе или команда `install <idx>` в Serial).
  Такие устройства защищены от LRU-вытеснения и сохраняются в NVS —
  переживают перезагрузку Хаба. Убрать их можно только явным `forget`.
  См. §"Установка устройств" ниже.

Для веб-интерфейса дополнительно кэшируется последнее известное
состояние клапана (`lastActiveValve`) из принятой телеметрии.

### Дедупликация

Ведётся отдельно на каждое устройство (по полю `lastSeenPacketId` в
записи таблицы) — в отличие от узла, который видит только одного
отправителя (Хаб) и обходится одним общим счётчиком.

### Веб-интерфейс

Хаб поднимает **собственную точку доступа Wi-Fi** (`WIFI_AP_STA`),
а не подключается к домашнему роутеру — осознанный выбор, чтобы не
зависеть от внешней сетевой инфраструктуры (в поле роутера может не
быть вообще, вместо него — GSM-модем) и не решать проблему
рассинхронизации радиоканала с чужим роутером: раз Хаб сам создаёт
точку доступа, канал (`ESPNOW_CHANNEL`) полностью в его руках.

- **SSID**: `SmartGarden-Hub` (константа `AP_SSID` в начале `hub.ino`)
- **Пароль**: `garden123` (константа `AP_PASSWORD` — **обязательно
  смените перед использованием**, минимум 8 символов — требование WPA2)
- **Адрес**: `http://192.168.4.1` (печатается в Serial при старте как
  `WiFi.softAPIP()`)

Подключитесь телефоном/ноутом к этой сети и откройте адрес в браузере.
Страница показывает таблицу известных устройств (автообновление каждые
2 сек через `fetch('/api/devices')`) с кнопками управления на каждое
устройство — тот же функционал, что и Serial-команды, просто с другого
входа. Сама HTML-страница (константа `INDEX_HTML`) вынесена в отдельный
файл `WebPage.h` рядом с `hub.ino` — Arduino IDE покажет его отдельной
вкладкой при открытии скетча.

**API** (для справки, если понадобится что-то ещё, кроме встроенной
страницы):

| Эндпоинт | Метод | Формат | Действие |
|---|---|---|---|
| `/` | GET | — | HTML-страница управления |
| `/api/devices` | GET | JSON-массив `{idx, mac, type, agoSec, activeValve, installed}` | Список известных устройств |
| `/api/command` | POST | `application/x-www-form-urlencoded`: `idx, valve, mode, duration, volume` | Отправить команду устройству (эквивалент `sendCommand()`) |
| `/api/install` | POST | `application/x-www-form-urlencoded`: `idx` | Подтвердить устройство: защитить от вытеснения, сохранить в NVS |
| `/api/forget` | POST | `application/x-www-form-urlencoded`: `idx` | Удалить устройство из таблицы (и из NVS, если было установлено) |
| `/api/settime` | POST | `application/x-www-form-urlencoded`: `epoch` (Unix-время в секундах, UTC) | Установить часы Хаба (вызывается автоматически самой страницей при каждой загрузке) |
| `/api/status` | GET | JSON `{timeSynced, epoch, timeString}` | Служебный статус Хаба, сейчас только про часы |

Веб-сервер и Serial-интерфейс работают **параллельно и независимо** —
можно пользоваться либо тем, либо другим, либо обоими одновременно.

### Установка устройств

Автоматическое обнаружение удобно, но ненадёжно на дистанции: любой
кандидат может быть вытеснен LRU при заполнении таблицы, а сама таблица
целиком живёт в RAM и очищается при перезагрузке Хаба (хотя и быстро
восстанавливается по трафику). Для устройств, физически установленных
на участке и остающихся там постоянно, это не годится — нужен явный
шаг подтверждения.

**Как это работает:**

1. Устройство появляется в таблице как обычный кандидат — по первому
   `MSG_CONFIG`/`MSG_TELEMETRY`, как и раньше.
2. Пользователь смотрит на него в веб-интерфейсе (можно предварительно
   опробовать клапан кнопками "Открыть"/"Закрыть", чтобы убедиться, что
   это именно то физическое устройство) и нажимает кнопку
   "Установить" (или `install <idx>` в Serial).
3. С этого момента устройство: (а) не участвует в LRU-вытеснении —
   `findOrRegisterDevice()` пропускает `installed=true` записи при
   поиске кандидата на вытеснение; (б) сохраняется в NVS
   (`Preferences`, пространство имён `smartgarden`, ключ `installed`) —
   при следующей загрузке Хаба `loadInstalledDevicesFromNVS()`
   восстанавливает его автоматически, до начала приёма ESP-NOW трафика.
4. Убрать установленное устройство можно только явно — кнопка
   "Забыть" (с подтверждением в браузере, действие разрушительное) или
   `forget <idx>` в Serial. Это удаляет запись и из таблицы, и из NVS.

В NVS хранится только необходимый минимум для повторного опознавания
устройства при следующей загрузке — MAC-адрес и тип устройства
(`InstalledDeviceRecord`). Оперативные поля (когда последний раз
выходило на связь, состояние клапана) не сохраняются — они
восстанавливаются из реального трафика после старта.

Если таблица окажется полностью занята установленными устройствами
(маловероятно при плановых 30-50 узлах и `MAX_DEVICES=64`, но в
принципе возможно) — новый необнаруженный кандидат просто не найдёт
себе места: в Serial появится предупреждение, а сам он не будет
добавлен, пока какое-то установленное устройство не забудут явно.

### Синхронизация времени

У Хаба нет RTC-модуля с батарейкой - при каждой перезагрузке внутренние часы
(`time()`/`settimeofday()`) сбрасываются на `1970-01-01`. Вместо NTP (который
требовал бы у Хаба выход в интернет, которого у него нет, см. выше) единственный
источник времени - браузер: веб-страница сама шлёт текущее UTC-время
(`POST /api/settime`) при каждой своей загрузке, а затем повторяет это раз в
30 минут (компенсация дрейфа часов ESP32), пока страница открыта в
браузере. Никакого ручного ввода от оператора не требуется.

Посмотреть результат синхронизации можно двумя способами:

- **В веб-интерфейсе** - строка-индикатор под шапкой страницы: зелёный
  текст с текущим временем Хаба, если синхронизация уже прошла, жёлтый -
  ожидание браузера.
- **В Serial Monitor** - команда `time` печатает текущий статус по запросу в
  любой момент - удобно, так как одноразовая строка лога в момент
  самой синхронизации быстро уходит вверх при активной работе (каждая
  принятая телеметрия и т.п. тоже пишет в Serial).

Всё время хранится и отображается в UTC, без перевода в местный часовой
пояс. Подробное обоснование выбора (почему не NTP, почему именно
30-минутный интервал пересинхронизации и т.д.) - в `../PROTOCOL.md` §12.

### Serial-интерфейс

Открыть Serial Monitor на **115200 бод**. Доступные команды:

| Команда | Действие |
|---|---|
| `list` | Показать все известные устройства (индекс, MAC, тип, когда последний раз выходили на связь, статус установки) |
| `open <idx> <valve> <sec>` | Открыть клапан `<valve>` на устройстве `<idx>` на `<sec>` секунд (`mode=0`) |
| `volume <idx> <valve> <liters>` | Открыть клапан `<valve>` на `<liters>` литров (`mode=1`, требует датчика потока на узле — пока не реализовано физически) |
| `close <idx>` | Закрыть все клапаны устройства `<idx>` |
| `install <idx>` | Подтвердить устройство: защитить от вытеснения, сохранить в NVS |
| `forget <idx>` | Удалить устройство из таблицы (и из NVS, если было установлено) |
| `time` | Показать текущее время Хаба и статус синхронизации с браузером |

`<idx>` — это индекс из вывода `list`, не MAC-адрес напрямую. Команду
нельзя отправить устройству, которое Хаб ещё ни разу не видел в эфире.

### При старте

1. Восстанавливает установленные устройства из NVS
   (`loadInstalledDevicesFromNVS()`) — до начала приёма ESP-NOW трафика,
   чтобы их слоты не могли быть заняты автообнаруженными кандидатами.
2. Поднимает точку доступа (`WiFi.softAP(AP_SSID, AP_PASSWORD, ESPNOW_CHANNEL)`)
   — канал задаётся явно тем же значением, что и в периферии.
3. Инициализирует ESP-NOW, регистрирует широковещательного пира.
4. Регистрирует HTTP-маршруты и запускает веб-сервер.
5. Трижды с паузой в 1 сек рассылает announce о своей загрузке
   (`sendHubAnnounce()`) — чтобы уже работающие узлы сбросили dedup.

## Известные ограничения текущей реализации

Подробный и актуальный список — `PROTOCOL.md` §7. Из специфичного для
Хаба:

- Serial- и веб-команды (`open`/`volume`/`close`) жёстко заточены под
  полив — при добавлении нового типа периферии (освещение и т.д.)
  потребуется свой набор команд/полей веб-страницы.
- Веб-интерфейс без авторизации — кто угодно, подключившийся к точке
  доступа (зная пароль Wi-Fi), может управлять клапанами. Приемлемо для
  текущего масштаба, но не забыть при расширении.
- Точка доступа Хаба не даёт телефону/ноуту доступ в интернет, пока к
  ней подключены — стандартное поведение для отдельной локальной сети
  (компромисс, на который сознательно пошли ради независимости от
  внешней инфраструктуры, см. `PROTOCOL.md` §10).

## На будущее

Согласно паспорту проекта (`../README.md`), финальный Хаб должен также
быть мостом в интернет (Wi-Fi/MQTT) — этого в текущей реализации нет.
Если впоследствии понадобится подключение к домашнему роутеру вместо
собственной точки доступа (или в дополнение к ней) — см. обсуждение
вариантов в `PROTOCOL.md` §10.
