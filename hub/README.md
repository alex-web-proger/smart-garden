# Hub

Центральный узел сети Smart Garden. Работает на **ESP32**. Слушает
широковещательный трафик ESP-NOW от всех периферийных устройств,
ведёт таблицу известных узлов и позволяет оператору отправлять им
команды — через Serial Monitor или через веб-интерфейс с телефона/ноута.

Подробное описание протокола, форматов сообщений и всех
задокументированных тонкостей — в [`../PROTOCOL.md`](../PROTOCOL.md).
Этот файл — про то, что конкретно делает скетч Хаба и как им пользоваться.

## Назначение

- Принимает от периферийных узлов `MSG_CONFIG` (паспорт устройства) и
  `MSG_TELEMETRY` (текущие показания), ведёт по ним таблицу устройств.
- Отправляет узлам `MSG_COMMAND` по команде оператора — из Serial или
  из браузера.
- Оповещает всю сеть о своей (пере)загрузке широковещательным
  `MSG_CONFIG` — это нужно узлам, чтобы корректно сбросить
  дедупликацию после рестарта Хаба (см. `PROTOCOL.md` §4.3).
- По кнопке на плате поднимает/гасит собственную Wi-Fi точку доступа
  с веб-страницей управления — состояние (включена/выключена)
  сохраняется в NVS и восстанавливается при перезагрузке (см. ниже).
- Ведёт часы: синхронизируется с браузером и, если на шине I2C
  обнаружена микросхема **DS3231**, дополнительно использует её как
  автономный источник времени, переживающий перезагрузку/отключение
  питания Хаба (см. ниже).
- Позволяет пользователю "установить" устройство через веб/Serial —
  подтверждённые устройства защищены от автоматического вытеснения,
  их можно переименовать, и они сохраняются в энергонезависимой
  памяти (NVS) вместе с названием, переживая перезагрузку Хаба (см.
  §"Установка устройств" ниже и `PROTOCOL.md` §11).

Хаб **не занимается** доменной логикой периферии (не знает, что такое
клапан или литр) — он только маршрутизирует пакеты и разбирает payload
для отображения (см. `handleIrrigationPayload()`).

## Структура файлов скетча

Логика разложена по нескольким файлам — Arduino IDE показывает их
отдельными вкладками того же окна при открытии `hub.ino`:

| Файл | Отвечает за |
|---|---|
| `hub.ino` | Протокол/ESP-NOW (включая очередь входящих пакетов), веб-API (HTTP-обвязка), часы Хаба, вкл/выкл точки доступа по кнопке, `setup()`/`loop()` |
| `DeviceManager.h/.cpp` | Таблица устройств: автообнаружение, `install`/`forget`, LRU-вытеснение, сохранение в NVS |
| `SerialCommands.h/.cpp` | Разбор команд Serial Monitor'а |
| `Ds3231Rtc.h/.cpp` | Опциональные часы реального времени DS3231 (детектирование, чтение/запись времени) |
| `ApButton.h/.cpp` | Антидребезг кнопки точки доступа (что именно делать по нажатию — решает `hub.ino`) |
| `WebPage.h` | HTML/JS страницы веб-интерфейса |

`DeviceManager`/`SerialCommands`/`Ds3231Rtc`/`ApButton` — обычные
`.cpp`-файлы, а не `.ino`-вкладки: в отличие от `.ino`, Arduino IDE не
склеивает их в один файл автоматически, поэтому доступ к глобальным
объектам `hub.ino` (`deviceManager`, `sendCommand()`, `timeSynced`,
`currentTimeString()`) из `SerialCommands.cpp` идёт через `extern` —
см. начало файла.

## Зависимости

- `<esp_now.h>`, `<WiFi.h>`, `<esp_wifi.h>` — стандартные для
  arduino-esp32 3.x. **Важно**: API `esp_now` здесь заметно отличается
  от ESP8266 (`<espnow.h>`), в частности сигнатура receive-колбэка и
  способ регистрации пира — см. комментарии в начале `hub.ino`.
  `esp_wifi_set_channel()` используется, чтобы зафиксировать радиоканал
  ESP-NOW независимо от того, включена ли в данный момент точка
  доступа (см. §"Кнопка и точка доступа").
- `<WebServer.h>` — встроенный в ядро arduino-esp32 HTTP-сервер, без
  внешних зависимостей (ArduinoJson и т.п. не используются — JSON для
  `/api/devices`/`/api/status` собирается вручную, ответ маленький).
- `<GardenProtocol.h>` из библиотеки `../libraries/GardenNet/` — общий
  формат пакета, дедупликация, общие MAC-константы (`BROADCAST_MAC`,
  `HUB_MAC`) и `fillPacketHeader()` (общая механика заполнения заголовка
  пакета, переиспользуемая и Хабом, и узлами). Хаб **не использует**
  класс `GardenNode` — тот написан для периферийных узлов с одним
  фиксированным адресатом (Хабом); у Хаба принципиально другая роль
  (много отправителей, произвольный адресат команды на каждый вызов,
  своя таблица устройств), поэтому вся логика маршрутизации реализована
  прямо в `hub.ino`, опираясь на общие протокольные примитивы из
  `GardenProtocol.h`, а не на класс.
- `<Preferences.h>` — встроенная в ядро arduino-esp32 обёртка над NVS
  (энергонезависимая flash-память ESP32), для хранения списка
  установленных устройств между перезагрузками. Используется внутри
  `DeviceManager`, не напрямую в `hub.ino`.
- `<Wire.h>` — стандартная библиотека I2C, для общения с DS3231 (если
  она физически подключена). `Ds3231Rtc` — собственный минимальный
  драйвер поверх неё, без внешних библиотек (тот же принцип "минимум
  зависимостей", что и с ручной сборкой JSON).
- `<ESPmDNS.h>` — встроенная в ядро arduino-esp32 реализация mDNS
  (Bonjour/zeroconf, в Linux обычно через avahi) — даёт доступ к
  веб-интерфейсу по доменному имени `http://smartgarden.local` вместо
  IP-адреса (см. §"Веб-интерфейс"), работает пока включена точка
  доступа.
- `<freertos/FreeRTOS.h>`, `<freertos/queue.h>` — часть ядра
  arduino-esp32 (уже присутствует в проекте неявно — `setup()`/`loop()`
  сами являются задачей FreeRTOS), используются явно для
  `incomingPacketQueue` — очереди входящих ESP-NOW-пакетов между
  колбэком приёма и `loop()` (см. «Oднопоточность бизнес-логики» ниже).

## Как это работает

### Таблица устройств

`DeviceManager::devices[MAX_DEVICES]` (`MAX_DEVICES=64`) двухуровневая:

- **Кандидаты** — заполняются автоматически по мере прихода
  `MSG_CONFIG`/`MSG_TELEMETRY` от новых MAC-адресов, никакой ручной
  регистрации не требуется (Plug & Play). Живут только в RAM, подлежат
  LRU-вытеснению при заполнении таблицы — подробности в `PROTOCOL.md`
  §6.2.
- **Установленные** — пользователь явно подтвердил устройство (кнопка
  "Установить" в веб-интерфейсе или команда `install <idx>` в Serial).
  Такие устройства защищены от LRU-вытеснения и сохраняются в NVS —
  переживают перезагрузку Хаба. Убрать их можно только явным `forget`.
  См. §"Установка устройств" ниже.

Для веб-интерфейса дополнительно кэшируется последнее известное
состояние клапана (`lastActiveValve`) из принятой телеметрии, а для
установленных устройств — заданное пользователем название (`name`, см.
§"Установка устройств").

Вся эта логика (поиск/регистрация, вытеснение, install/forget,
сохранение в NVS) инкапсулирована в классе `DeviceManager`
(`DeviceManager.h/.cpp`) — и `hub.ino` (веб-API, `onDataRecv()`), и
`SerialCommands.cpp` обращаются к одному и тому же глобальному
экземпляру `deviceManager`, а не дублируют логику каждый на своей
стороне (раньше `install`/`forget` были продублированы отдельно для
Serial-команд и отдельно для веб-API — теперь это один метод на оба
входа).

### Дедупликация

Ведётся отдельно на каждое устройство (по полю `lastSeenPacketId` в
записи таблицы) — в отличие от узла, который видит только одного
отправителя (Хаб) и обходится одним общим счётчиком.

### Однопоточность бизнес-логики

Ядро arduino-esp32 вызывает колбэк приёма ESP-NOW (`onDataRecv()`) из
собственной задачи FreeRTOS (стек радио), а не из `loop()`. Без
особых мер это значило бы, что таблица устройств (`deviceManager`) и
исходящий пакет (`txPacket`) читались/писались бы из двух разных
задач одновременно с `loop()` (Serial-команды, обработчики веб-API) —
классическая гонка данных.

Решение — очередь `incomingPacketQueue` (FreeRTOS `QueueHandle_t`), а не
мьютексы/критические секции:

- `onDataRecv()` (задача Wi-Fi) делает МИНИМУМ — проверяет размер,
  копирует пакет и кладёт его в очередь без блокировки
  (`xQueueSend(..., 0)`) — если очередь вдруг переполнена, пакет молча
  теряется (придёт снова со следующей телеметрией) — это лучше, чем
  задерживать саму задачу стека Wi-Fi.
- вся содержательная обработка (поиск/регистрация в `deviceManager`,
  дедупликация, разбор payload) — в `processIncomingPacket()`, которую
  `loop()` вызывает для каждого накопившегося в очереди пакета.

В итоге вся бизнес-логика Хаба — и обработка входящих пакетов, и
Serial-команды, и обработчики веб-API — выполняется одной единственной
задачей (`loop()`). Гонка устранена не блокировками, а тем, что делить
нечего — у состояния один владелец. `DeviceManager.h` явно фиксирует это
как требование к вызывающему коду, на будущее.

### Кнопка, точка доступа и статус радио

Точка доступа веб-интерфейса **выключена по умолчанию для самого
первого запуска** (когда в NVS ещё ничего не сохранено) — устройство не
начинает вещать Wi-Fi-сеть само по себе. Включает и выключает её
физическая кнопка на плате — антидребезг вынесен в отдельный класс
`ApButton` (`ApButton.h/.cpp`), а что делать по нажатию — решает
`hub.ino` (`setApEnabled()`). Само состояние (включена/выключена)
**переживает перезагрузку Хаба** — сохраняется в NVS при каждом нажатии
кнопки (`saveApEnabledToNVS()`) и восстанавливается в `setup()`
(`loadApEnabledFromNVS()`) — то есть после перезагрузки Хаб возвращается
в то же состояние AP, в котором был до этого, а не всегда стартует с
выключенной.

- `AP_BUTTON_PIN = 0` — кнопка **BOOT**, присутствующая на подавляющем
  большинстве отладочных плат ESP32 с модулем WROOM (сам модуль
  кнопок не имеет — они на плате-носителе). Подтянута к VCC на плате,
  замыкается на GND при нажатии (`INPUT_PULLUP`, активный уровень
  `LOW`), опрашивается через `ApButton::wasPressed()` в каждой итерации
  `loop()`, с антидребезгом по времени (50 мс).
- `AP_LED_PIN = 2` — встроенный светодиод, присутствующий на
  большинстве таких плат. У него двойное назначение (см. ниже).

Если у конкретной платы распиновка другая — поменять оба `#define` в
начале `hub.ino`.

**Важно**: радиоканал ESP-NOW (`ESPNOW_CHANNEL`) фиксируется в
`setup()` через `esp_wifi_set_channel()` сразу после `WiFi.mode()`,
**независимо** от состояния точки доступа. Поэтому приём и отправка
ESP-NOW-пакетов (включая обработку телеметрии от узлов) работает
всегда, даже когда AP выключена кнопкой — выключается именно точка
доступа для веб-интерфейса, а не радиосвязь с полем.

**Статус радио**: если `esp_now_init()`/`esp_now_add_peer()` в `setup()`
провалились (флаг `radioReady == false`) — тот же светодиод `AP_LED_PIN`
начинает быстро мигать (`updateStatusLed()`, каждые 250 мс) — это
ПЕРЕОПРЕДЕЛЯЕТ обычную индикацию точки доступа: без ESP-NOW Хаб
бесполезен как центр сети (не примет и не отправит ни одного пакета
периферии), это критичнее статуса точки доступа — веб-интерфейс и
Serial при этом остаются доступны (достаточно для диагностики на месте). Как
только радио в порядке, светодиод возвращается к обычной индикации статуса AP.

### Веб-интерфейс

Когда точка доступа включена, Хаб поднимает **собственную** Wi-Fi-сеть
(`WiFi.softAP(...)`), а не подключается к домашнему роутеру —
осознанный выбор, чтобы не зависеть от внешней сетевой инфраструктуры
(в поле роутера может не быть вообще, вместо него — GSM-модем) и не
решать проблему рассинхронизации радиоканала с чужим роутером: раз Хаб
сам создаёт точку доступа, канал (`ESPNOW_CHANNEL`) полностью в его
руках.

- **SSID**: `SmartGarden-Hub` (константа `AP_SSID` в начале `hub.ino`)
- **Пароль**: `garden123` (константа `AP_PASSWORD` — **обязательно
  смените перед использованием**, минимум 8 символов — требование WPA2)
- **Адрес**: `http://192.168.4.1` (печатается в Serial в момент
  включения точки доступа как `WiFi.softAPIP()`)

Нажмите кнопку на плате, чтобы включить точку доступа (загорится
светодиод), затем подключитесь телефоном/ноутом к этой сети и откройте
адрес в браузере — либо `http://192.168.4.1`, либо (если устройство
поддерживает mDNS) **`http://smartgarden.local`** — доменное имя
(`HUB_HOSTNAME` в `hub.ino`) запускается вместе с точкой доступа
(`restartMDNS()`) и останавливается при её выключении. Поддержка mDNS на
стороне клиента не гарантирована на 100% (из коробки работает на
iOS/macOS, обычно на Linux с avahi и на большинстве современных
Android; на Windows зависит от наличия Bonjour Print Services) — если
`.local`-адрес не резолвится, достаточно зайти по IP. Страница показывает
таблицу известных устройств (автообновление каждые 2 сек через
`fetch('/api/devices')`) с кнопками управления на каждое устройство — тот же
функционал, что и Serial-команды, просто с другого входа. Сама HTML-страница
(константа `INDEX_HTML`) вынесена в отдельный файл `WebPage.h` рядом с
`hub.ino`.

**API** (для справки, если понадобится что-то ещё, кроме встроенной
страницы):

| Эндпоинт | Метод | Формат | Действие |
|---|---|---|---|
| `/` | GET | — | HTML-страница управления |
| `/api/devices` | GET | JSON-массив `{idx, mac, type, name, agoSec, activeValve, installed}` | Список известных устройств |
| `/api/command` | POST | `application/x-www-form-urlencoded`: `idx, valve, action, mode, duration, volume` (`volume` дробное, например `2.5` для `mode=2`) | Отправить команду устройству (эквивалент `sendCommand()`) |
| `/api/install` | POST | `application/x-www-form-urlencoded`: `idx` | Подтвердить устройство: защитить от вытеснения, сохранить в NVS |
| `/api/forget` | POST | `application/x-www-form-urlencoded`: `idx` | Удалить устройство из таблицы (и из NVS, если было установлено) |
| `/api/rename` | POST | `application/x-www-form-urlencoded`: `idx, name` | Задать/сменить название — ТОЛЬКО для установленного устройства, сохраняется в NVS |
| `/api/settime` | POST | `application/x-www-form-urlencoded`: `epoch` (целое число секунд, МЕСТНОЕ время браузера, не UTC) | Установить часы Хаба (вызывается автоматически самой страницей при каждой загрузке); если обнаружена DS3231, время попутно записывается и в неё |
| `/api/status` | GET | JSON `{timeSynced, epoch, timeString, rtcPresent, apEnabled, radioReady}` | Служебный статус Хаба: часы, обнаружена ли DS3231, включена ли точка доступа, готово ли радио ESP-NOW |

Веб-сервер и Serial-интерфейс работают **параллельно и независимо** —
можно пользоваться либо тем, либо другим, либо обоими одновременно. Сам
HTTP-сервер запускается в `setup()` безусловно (не дожидаясь нажатия
кнопки) — просто до включения точки доступа он физически недостижим:
подключиться к нему по Wi-Fi не от кого.

### Установка устройств

Автоматическое обнаружение удобно, но ненадёжно на дистанции: любой
кандидат может быть вытеснен LRU при заполнении таблицы, а сама таблица
целиком живёт в RAM и очищается при перезагрузке Хаба (хотя и быстро
восстанавливается по трафику). Для устройств, физически установленных
на участке и остающихся там постоянно, это не годится — нужен явный
шаг подтверждения.

**Как это работает:**

1. Устройство появляется в таблице как обычный кандидат — по первому
   `MSG_CONFIG`/`MSG_TELEMETRY`, как и раньше.
2. Пользователь смотрит на него в веб-интерфейсе (можно предварительно
   опробовать клапан кнопками "Открыть"/"Закрыть", чтобы убедиться, что
   это именно то физическое устройство) и нажимает кнопку
   "Установить" (или `install <idx>` в Serial).
3. С этого момента устройство: (а) не участвует в LRU-вытеснении —
   `DeviceManager::findOrRegister()` пропускает `installed=true` записи
   при поиске кандидата на вытеснение; (б) сохраняется в NVS
   (`Preferences`, пространство имён `smartgarden`, ключ `installed`) —
   при следующей загрузке Хаба `DeviceManager::loadFromNVS()`
   восстанавливает его автоматически, до начала приёма ESP-NOW трафика.
4. Можно задать/сменить название устройства — поле "Название" в
   модальном окне веб-интерфейса или `rename <idx> <название>` в Serial
   (`DeviceManager::setName()`) — ДОСТУПНО ТОЛЬКО для уже установленного
   устройства (у кандидата название всё равно не переживёт его возможное
   вытеснение), сохраняется в NVS вместе с остальными данными
   установленного устройства. Обрезается до `DEVICE_NAME_MAX_LEN-1` = 23
   символов (`DeviceManager.h`).
5. Убрать установленное устройство можно только явно — кнопка
   "Забыть" (с подтверждением в браузере, действие разрушительное) или
   `forget <idx>` в Serial. Это удаляет запись и из таблицы, и из NVS.

В NVS хранится только необходимый минимум для повторного опознавания
устройства при следующей загрузке — MAC-адрес, тип устройства и название
(`InstalledDeviceRecord`). Оперативные поля (когда последний раз выходило на
связь, состояние клапана) не сохраняются — они
восстанавливаются из реального трафика после старта.

Если таблица окажется полностью занята установленными устройствами
(маловероятно при плановых 30-50 узлах и `MAX_DEVICES=64`, но в
принципе возможно) — новый необнаруженный кандидат просто не найдёт
себе места: в Serial появится предупреждение, а сам он не будет
добавлен, пока какое-то установленное устройство не забудут явно.

### Синхронизация времени

У ESP32 нет собственных часов на батарейке — без внешнего RTC-модуля
внутренние часы (`time()`/`settimeofday()`) сбрасываются на
`1970-01-01` при каждой перезагрузке. У Хаба теперь два источника
времени:

- **Браузер** — как и раньше: веб-страница сама шлёт текущее МЕСТНОЕ
  время (не UTC — свой часовой пояс браузер вычисляет сам через
  `getTimezoneOffset()`, фоллбэк — часовой пояс Киева) (`POST
  /api/settime`) при каждой своей загрузке, а затем повторяет это раз
  в 30 минут (компенсация дрейфа часов ESP32), пока страница открыта.
  Требует, разумеется, чтобы точка доступа была включена и кто-то
  открыл страницу — то есть недоступен сразу после холодного старта
  Хаба, если рядом никого нет.
- **DS3231** (опционально, если физически подключена по I2C) —
  автономный источник, не зависящий ни от браузера, ни от точки
  доступа: работает на собственной батарейке и переживает
  перезагрузку/полное отключение питания Хаба. При старте, ДО
  восстановления таблицы устройств из NVS, Хаб пытается обнаружить
  микросхему на шине (`Ds3231Rtc::begin()`, адрес `0x68`) и сразу
  печатает в Serial, обнаружена она или нет:
  - **Обнаружена и время достоверно** — Хаб немедленно выставляет
    системные часы из показаний DS3231, не дожидаясь браузера/точки
    доступа. "Достоверно" проверяется по флагу `OSF` (Oscillator Stop
    Flag) самой микросхемы — он показывает, не было ли потери питания
    часов с момента последней записи времени; если был — время в
    регистрах не заслуживает доверия (типичная ситуация для свежей
    микросхемы без ранее заданного времени или с разряженной резервной
    батарейкой), Хаб это пропускает и ждёт синхронизации с браузером,
    как обычно.
  - **Не обнаружена** — поведение как раньше: единственный источник
    времени — браузер.

  Синхронизация — в обе стороны: при каждой успешной `POST
  /api/settime` от браузера новое время попутно записывается и в
  DS3231 (`Ds3231Rtc::setEpoch()`, заодно сбрасывает `OSF`) — так она
  не отстаёт от последнего известного правильного времени и хранит его
  дальше автономно, даже если Хаб потом надолго обесточат.

  Драйвер (`Ds3231Rtc.h/.cpp`) — собственный, минимальный, поверх
  `<Wire.h>`, без внешних библиотек (тот же принцип, что и с ручной
  сборкой JSON для веб-API): чтение/запись регистров времени напрямую,
  BCD-конвертация, пересчёт год/месяц/день/час/минута/секунда в
  unix-эпоху и обратно — собственная реализация алгоритма Хауарда
  Хиннанта (`days_from_civil`/`civil_from_days`), а не
  `mktime()`/`timegm()`, чтобы не зависеть от timezone-таблиц рантайма,
  которых на ESP32 без отдельной библиотеки часовых поясов нет.

С Хаба то же время автоматически разлетается по ESP-NOW всем
периферийным узлам — в том числе НЕМЕДЛЕННО, сразу как только
какой-то узел прислал свой собственный `MSG_CONFIG` (то есть сразу
после своей перезагрузки) — чтобы он не ждал свою очередную
синхронизацию часами/до 30 минут. Подробнее — `../PROTOCOL.md` §12.6.

Посмотреть результат синхронизации можно двумя способами:

- **В браузере** — индикатор `#time-status` под шапкой страницы,
  подгружается через `GET /api/status` каждые 2 сек вместе со списком
  устройств: зелёный текст с текущим временем Хаба, если синхронизация
  уже прошла, жёлтый — ожидание.
- **В Serial Monitor** — команда `time` печатает текущий статус по
  запросу в любой момент — удобно, так как одноразовая строка лога в
  момент самой синхронизации быстро уходит вверх при активной работе
  (каждая принятая телеметрия и т.п. тоже пишет в Serial).

Всё время хранится и отображается МЕСТНЫМ, не UTC — сдвиг на часовой
пояс целиком происходит на стороне браузера до отправки (то же
местное значение потом хранится и в DS3231) — Хаб просто хранит
полученное значение. Подробное обоснование выбора (почему не NTP,
киевский фоллбэк, почему именно 30-минутный интервал пересинхронизации
и т.д.) — в `../PROTOCOL.md` §12.

### Serial-интерфейс

Открыть Serial Monitor на **115200 бод**. Доступные команды (разбор —
в `SerialCommands.cpp`):

| Команда | Действие |
|---|---|
| `list` | Показать все известные устройства (индекс, MAC, тип, когда последний раз выходили на связь, статус установки) |
| `open <idx> <valve> <sec>` | Открыть клапан `<valve>` на устройстве `<idx>` на `<sec>` секунд (`mode=0`) |
| `volume <idx> <valve> <liters>` | Открыть клапан `<valve>` на `<liters>` целых литров (`mode=1`, легаси-режим, НЕ реализован на узле) |
| `dose <idx> <valve> <liters>` | ТРЕТИЙ РЕЖИМ: точная дозировка на `<liters>` литров с точностью до 0.1 л (`mode=2`, `<liters>` дробное, например `2.5`) — РЕАЛИЗОВАН на узле, требует настроенного датчика потока, всегда открывает РОВНО один клапан, форсированно закрывая остальные |
| `close <idx>` | Закрыть все клапаны устройства `<idx>` |
| `install <idx>` | Подтвердить устройство: защитить от вытеснения, сохранить в NVS |
| `forget <idx>` | Удалить устройство из таблицы (и из NVS, если было установлено) |
| `rename <idx> <название>` | Переименовать УСТАНОВЛЕННОЕ устройство, сохранить в NVS |
| `time` | Показать текущее время Хаба и статус синхронизации (с браузером и/или DS3231) |

`<idx>` — это индекс из вывода `list`, не MAC-адрес напрямую. Команду
нельзя отправить устройству, которое Хаб ещё ни разу не видел в эфире.
Точка доступа кнопкой не управляется из Serial — только физической
кнопкой на плате.

### При старте

1. Настраивает пин светодиода (`OUTPUT`, гасит его) и инициализирует
   `ApButton` — точка доступа выключена, пока её явно не включат.
2. Обнаруживает DS3231 на шине I2C (`rtc.begin()`) — печатает в Serial,
   найдена она или нет; если найдена и время достоверно, сразу
   выставляет системные часы из неё.
3. Восстанавливает установленные устройства из NVS
   (`deviceManager.loadFromNVS()`) — до начала приёма ESP-NOW трафика,
   чтобы их слоты не могли быть заняты автообнаруженными кандидатами.
4. Переводит Wi-Fi в режим `WIFI_AP_STA` и фиксирует радиоканал
   ESP-NOW (`esp_wifi_set_channel()`) — саму точку доступа при этом
   **не** включает.
5. Создаёт очередь `incomingPacketQueue`, затем инициализирует ESP-NOW
   и регистрирует широковещательного пира — если что-то из этого не
   удалось, `radioReady` остаётся `false`, и с следующего тика `loop()`
   светодиод начнёт быстро мигать (см. «Статус радио» выше).
6. Восстанавливает состояние точки доступа из NVS
   (`loadApEnabledFromNVS()`) и применяет его через `setApEnabled()` — УЖЕ
   ПОСЛЕ того, как определился `radioReady` на предыдущем шаге, чтобы
   светодиод сразу корректно отразил восстановленное состояние (не
   перезаписывая его же в NVS повторно).
7. Регистрирует HTTP-маршруты и запускает веб-сервер — независимо от
   того, готово ли радио: веб-интерфейс нужен для диагностики даже если
   ESP-NOW не заработал.
8. Если радио готово — трижды с паузой в 1 сек рассылает announce о своей
   загрузке (`sendHubAnnounce()`) — чтобы уже работающие узлы сбросили
   dedup; работает независимо от состояния точки доступа, это ESP-NOW, а
   не Wi-Fi AP.

## Известные ограничения текущей реализации

Подробный и актуальный список — `PROTOCOL.md` §7. Из специфичного для
Хаба:

- Serial- и веб-команды (`open`/`volume`/`dose`/`close`) жёстко заточены под
  полив — при добавлении нового типа периферии (освещение и т.д.)
  потребуется свой набор команд/полей веб-страницы.
- Веб-интерфейс без авторизации — кто угодно, подключившийся к точке
  доступа (зная пароль Wi-Fi), может управлять клапанами. Приемлемо для
  текущего масштаба, но не забыть при расширении.
- Точка доступа Хаба не даёт телефону/ноуту доступ в интернет, пока к
  ней подключены — стандартное поведение для отдельной локальной сети
  (компромисс, на который сознательно пошли ради независимости от
  внешней инфраструктуры, см. `PROTOCOL.md` §10).
- `AP_BUTTON_PIN`/`AP_LED_PIN` — дефолты для типовых плат ESP32 DevKit
  с модулем WROOM (кнопка BOOT на GPIO0, светодиод на GPIO2). На платах
  с другой распиновкой нужно поменять эти `#define` перед прошивкой.
- Светодиод `AP_LED_PIN` совмещает две роли — статус точки доступа и
  сигнал об отказе радио (см. «Кнопка, точка доступа и статус радио») —
  если появится третья причина для индикации (например, низкий заряд
  батареи) — одного светодиода может не хватить — потребуется либо
  второй, либо более сложный паттерн мигания.
- `INCOMING_QUEUE_LENGTH = 16` — глубина очереди входящих пакетов (см.
  «Однопоточность бизнес-логики») подобрана эмпирически, под типичную
  частоту телеметрии (в среднем меньше одного пакета в секунду при
  плановых 30-50 узлах). При заметно большем числе узлов или более
  частой телеметрии имеет смысл пересчитать с запасом.

## На будущее

Согласно паспорту проекта (`../README.md`), финальный Хаб должен также
быть мостом в интернет (Wi-Fi/MQTT) — этого в текущей реализации нет.
Если впоследствии понадобится подключение к домашнему роутеру вместо
собственной точки доступа (или в дополнение к ней) — см. обсуждение
вариантов в `PROTOCOL.md` §10.

Когда появится сетевая синхронизация с внешним сервером (Laravel) —
скорее всего, её стоит вынести в отдельную задачу FreeRTOS
(`xTaskCreate`) со своим приоритетом/стеком, а не вызывать напрямую из
`loop()`: блокирующий сетевой вызов (TLS-хендшейк, таймауты) иначе
будет задерживать обработку ESP-NOW-трафика и веб-запросов оператора.
Стоит придерживаться того же паттерна, что и для `onDataRecv()` (см.
«Однопоточность бизнес-логики»): новая задача кладёт результаты в
очередь, а их обработку (включая любое обращение к `deviceManager`) делает
`loop()` — так `DeviceManager` останется единственно владеющим своего
состояния и после такого добавления, без новых гонок и без необходимости
добавлять туда мьютексы. До этого момента текущая кооперативная модель
(`setup()`/`loop()` + очередь для ESP-NOW, без дополнительных задач) справляется
с нагрузкой Хаба без проблем.
