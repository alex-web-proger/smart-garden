# Протокол Smart Garden (ESP-NOW)

Описывает формат пакета и обмен сообщениями между устройствами проекта:
`hub` (ESP32), `flow_node` (ESP8266, полив), `relay` (ESP8266, ретранслятор).
Транспорт — ESP-NOW в режиме broadcast (`FF:FF:FF:FF:FF:FF`), радиоканал
фиксирован константой `ESPNOW_CHANNEL` (сейчас `1`) и должен
совпадать на всех устройствах сети.

Протокол (структуры пакета, дедупликация) и переиспользуемая логика
периферийного узла (джиттер, watchdog, авто-ACK) вынесены в отдельную
Arduino-библиотеку `libraries/GardenNet/` — единственный источник правды,
без ручного дублирования между папками скетчей (как было раньше с `common.h`).
Подробно об архитектуре библиотеки — в §9.

Структуры и константы, описанные ниже, определены в `GardenProtocol.h`
внутри библиотеки и подключаются всеми тремя скетчами через
`#include <GardenProtocol.h>`.

Структура папок проекта:

```
smart_garden/
├── hub/                  - Хаб (ESP32), один на всю сеть
├── relay/                - ретранслятор (ESP8266), пока тоже один
├── modules/               - периферийные устройства (по папке на тип)
│   └── flow_node/         - узел полива (ESP8266) - сейчас единственный модуль
├── libraries/GardenNet/   - общий протокол + переиспользуемая логика узла
├── PROTOCOL.md            - этот файл
└── TESTING.md
```

`hub` и `relay` вынесены на верхний уровень отдельно от `modules/`,
потому что они инфраструктурные и всегда существуют в единственном
экземпляре — в отличие от периферийных модулей, которых со временем
станет несколько (полив, освещение, ...).

## 1. Формат пакета (`UniversalPacket`)

Вся структура передаётся по радио как есть (`memcpy` в буфер `esp_now_send`),
поэтому зафиксирована `#pragma pack(push, 1)` — без этого компилятор может
добавить выравнивающие байты, и layout в памяти ESP8266 и ESP32 (разные
тулчейны) может не совпасть.

| Поле | Тип | Назначение |
|---|---|---|
| `sender_mac[6]` | `uint8_t[6]` | MAC устройства-источника. Зашит внутри пакета (а не берётся с радиоуровня), чтобы сохраняться при прохождении через ретранслятор. |
| `receiver_mac[6]` | `uint8_t[6]` | Кому адресован пакет. `00:00:00:00:00:00` — маркер "адресовано Хабу". `FF:FF:FF:FF:FF:FF` — широковещательно всем устройствам (используется Хабом при объявлении о (пере)загрузке, см. §3.2/§4.3). Реальный MAC узла — адресовано конкретному периферийному устройству. |
| `packet_id` | `uint16_t` | Порядковый номер пакета от данного отправителя. Используется для дедупликации, см. §4. Переполняется на 65536-м пакете. |
| `hop_count` | `uint8_t` | `0` — оригинал. `1` — уже прошёл через один ретранслятор. См. §5. |
| `device_type` | `uint8_t` (`DeviceType`) | `TYPE_HUB=0`, `TYPE_IRRIGATION=1`, `TYPE_WEATHER=2` (последний пока не реализован). |
| `msg_type` | `uint8_t` (`MsgType`) | `MSG_CONFIG=1`, `MSG_TELEMETRY=2`, `MSG_COMMAND=3`, `MSG_ACK=4`. |
| `payload` | `union` | Содержимое зависит от `device_type` + `msg_type`, см. §3. |

Фактический размер пакета (irrigation, с текущим payload) — около 28 байт
с упаковкой. Лимит ESP-NOW — 250 байт полезной нагрузки; на этапе
компиляции это проверяется через `static_assert(sizeof(UniversalPacket) <= 250, ...)`
в `GardenProtocol.h` — если правки в `payload` когда-нибудь превысят лимит,
сборка не пройдёт, а не сломается тихо в рантайме.

## 2. Кто есть кто в сети

| Устройство | Роль | `device_type` при отправке | Инициирует пакеты |
|---|---|---|---|
| `hub` (ESP32) | Центр, слушает всех, шлёт команды | `TYPE_HUB` | `MSG_COMMAND` (по команде оператора через Serial) |
| `flow_node` (ESP8266) | Узел полива | `TYPE_IRRIGATION` | `MSG_CONFIG`, `MSG_TELEMETRY`, `MSG_ACK` |
| `relay` (ESP8266) | Ретранслятор | — | Ничего своего не генерирует, только пересылает чужие пакеты как есть (см. §5) |

## 3. Кто что посылает и когда

### 3.1. `flow_node` → Хаб

| `msg_type` | Когда отправляется | `receiver_mac` | Payload |
|---|---|---|---|
| `MSG_CONFIG` | Сразу при загрузке устройства + повторно ~раз в час (база `CONFIG_INTERVAL_MS`=3600000, джиттер ±`CONFIG_JITTER_MS`=300000) | `00:00:00:00:00:00` (Хаб) | `IrrigationSpec { valve_count, has_flow_sensor }` |
| `MSG_TELEMETRY` | Каждые ~10 секунд (база `TELEMETRY_INTERVAL_MS`=10000, джиттер ±`TELEMETRY_JITTER_MS`=2000) | `00:00:00:00:00:00` (Хаб) | `IrrigationTelemetry { active_valve, current_flow, total_water_used }` |
| `MSG_ACK` | Сразу после обработки принятой `MSG_COMMAND` | `00:00:00:00:00:00` (Хаб) | `AckData { acked_packet_id, status }` |

Джиттер пересчитывается заново после каждой отправки (а не разово при старте) —
см. §6.2.

Повторная отправка `MSG_CONFIG` — это не просто "напоминание о
себе": получатель обязан трактовать любой `MSG_CONFIG` от устройства как
сигнал "устройство только что (пере)загрузилось" и сбросить для него
dedup-счётчик (см. §4). Из-за этого не стоит слать `MSG_CONFIG` слишком
часто без необходимости — а слишком редко тоже плохо, если единственный
способ Хаба узнать о перезагрузке узла — это именно `MSG_CONFIG`.

### 3.2. Хаб → `flow_node`

| `msg_type` | Когда отправляется | `receiver_mac` | Payload |
|---|---|---|---|
| `MSG_CONFIG` | 3 раза с интервалом 1 сек сразу при загрузке Хаба (`sendHubAnnounce()`) | `FF:FF:FF:FF:FF:FF` (всем) | Не используется (пустой payload) |
| `MSG_COMMAND` | По команде оператора в Serial Monitor Хаба (`open`/`volume`/`close`) | Реальный MAC конкретного узла (берётся из таблицы `devices[]`, куда узел попадает после первого `MSG_CONFIG`/`MSG_TELEMETRY`) | `IrrigationCommand { target_valve, mode, duration_sec, volume_l }` |

`MSG_CONFIG` от Хаба — это не "паспорт" в смысле характеристик (у Хаба
нет полей вроде `valve_count`), а announce о (пере)загрузке: узлы,
увидев `device_type==TYPE_HUB && msg_type==MSG_CONFIG`, обязаны
сбросить свой dedup-счётчик для Хаба, см. §4.3.

Команду нельзя послать устройству, которое Хаб ещё не "увидел" — Хаб
узнаёт MAC узла только из входящих `MSG_CONFIG`/`MSG_TELEMETRY`, поэтому
`open <idx> ...` работает только по индексу из `list`, а не "вслепую".

`IrrigationCommand.mode`:
- `0` — команда на N секунд (`duration_sec`). Не требует датчика потока.
- `1` — команда на N литров (`volume_l`). Требует датчика потока
  (`has_flow_sensor` из `MSG_CONFIG`) — **на узле эта логика ещё не
  реализована**, см. §7.

### 3.3. `relay` — ничего "своего" не посылает

Ретранслятор не участвует в протоколе как отправитель/получатель — он
слепо копирует чужие пакеты, меняя только `hop_count`. Он не разбирает
`payload`, не ведёт список устройств и не отвечает `MSG_ACK` за них.
Подробности — §5.

## 4. Адресация и дедупликация

### 4.1. Кому адресован пакет

- `receiver_mac == 00:00:00:00:00:00` — пакет для Хаба. Периферия
  игнорирует такие пакеты (кроме самого Хаба).
- `receiver_mac == FF:FF:FF:FF:FF:FF` — пакет для всех устройств сразу.
  Сейчас единственный пример — announce Хаба о (пере)загрузке (§3.2).
  Узлы принимают такие пакеты в дополнение к адресованным лично им.
- `receiver_mac == <реальный MAC>` — пакет для конкретного узла. Хаб
  игнорирует пакеты не с "нулевым" адресом (то есть команды других
  устройств друг другу, если такое появится, Хаб не перехватывает).

Узел проверяет оба своих варианта (`addressedToMe || addressedToAll`)
побайтовым `memcmp`; Хаб — только точное совпадение с нулевым маркером.
Если ни один вариант не подошёл — пакет молча отбрасывается.

### 4.2. `packet_id` и `isNewerPacketId()`

Дедупликация нужна по двум причинам: (а) устройство может слышать один и
тот же пакет дважды — напрямую и через ретранслятор; (б) защита от
случайной повторной обработки команд.

```cpp
inline bool isNewerPacketId(uint16_t incoming, uint16_t lastSeen) {
    uint16_t diff = incoming - lastSeen;
    return diff != 0 && diff < 0x8000;
}
```

Это циклическое сравнение (как sequence numbers в TCP):
- Корректно обрабатывает переполнение `uint16_t` (65535 → 0).
- **Точный дубликат** (`incoming == lastSeen`) явно отклоняется —
  до недавнего момента здесь была ошибка (равенство ошибочно считалось
  "новее"), из-за которой дубликат через ретранслятор проходил бы дважды.
  Сейчас исправлено.

**На Хабе** dedup ведётся **отдельно на каждое устройство** (таблица
`devices[]`, поле `lastSeenPacketId` на MAC). **На узле** — один общий
счётчик `lastReceivedCommandId`, потому что единственный отправитель
команд узлу — Хаб.

### 4.3. Сброс dedup при перезагрузке — реализовано в обе стороны

Приём `MSG_CONFIG` от устройства трактуется получателем как "это
устройство только что перезагрузилось" → dedup-счётчик для него
обнуляется **до** проверки `isNewerPacketId()` для этого же пакета
(иначе само announce-сообщение имело бы шанс быть отклонённым как
"старое").

- Хаб делает это для входящих `MSG_CONFIG` от узлов
  (`devices[idx].lastSeenPacketId = 0` в `onDataRecv()`).
- Узел делает симметричное: получив broadcast `MSG_CONFIG` с
  `device_type == TYPE_HUB` (см. §3.2), сбрасывает
  `lastReceivedCommandId = 0`.

Без этого механизма перезагрузка Хаба означала бы следующее: его
исходящий `lastPacketId` обнуляется, и первая команда после рестарта
приходит узлу с маленьким `packet_id` (например, `1`), в то время как
узел уже видел от Хаба, скажем, `id=50`. `isNewerPacketId(1, 50)`
вернула бы `false` — команда была бы молча отклонена как "старая", и
так продолжалось бы, пока новый счётчик Хаба не долистает обратно до
`50+`. Announce на broadcast-адрес закрывает эту проблему: узел
получает сигнал о перезагрузке Хаба независимо от конкретных значений
счётчиков.

Остаточный риск: если ни одна из 3 попыток announce не дойдёт до узла
(например, узел временно вне зоны действия при старте Хаба и не в
сети ни один ретранслятор), проблема проявится как раньше — узел не
узнает о перезагрузке Хаба до тех пор, пока packet_id снова не
догонит прежнее значение.

## 5. Ретранслятор и `hop_count`

`relay` слушает broadcast и для каждого принятого пакета:

1. Если `hop_count != 0` (уже был ретранслирован кем-то) — **ничего не
   делает**. Это единственный механизм анти-петли: пакет физически не
   может пройти больше одного "прыжка" через репку, даже если несколько
   репок слышат друг друга.
2. Если `hop_count == 0` — устанавливает `hop_count = 1` и пересылает
   пакет как broadcast **без изменения остальных полей**, включая
   `sender_mac`/`receiver_mac`/`packet_id`/`payload`. Payload не
   разбирается вообще.

**У `relay` намеренно нет собственного dedup.** Если бы репка ошибочно
решила "этот пакет уже пересылался" и пропустила пересылку — а она
единственный путь до узла вне прямой досягаемости Хаба — команда не
дошла бы вообще, без какого-либо признака ошибки. Лишняя же пересылка
безвредна: конечный узел/Хаб сам корректно отбросит дубликат через
`isNewerPacketId()` (§4.2). Поэтому репка форвардит каждый оригинал
безусловно.

Следствие: если один узел слышит и Хаб напрямую, и репку — он получит
**два одинаковых пакета** (`hop_count=0` и `hop_count=1`, одинаковый
`packet_id`). Дедупликация на узле уберёт вторую копию.

## 6. Payload по типам сообщений (`TYPE_IRRIGATION`)

| Структура | Используется в | Поля |
|---|---|---|
| `IrrigationSpec` | `MSG_CONFIG` | `valve_count` (кол-во клапанов), `has_flow_sensor` (0/1) |
| `IrrigationTelemetry` | `MSG_TELEMETRY` | `active_valve` (0=закрыто, 1..N=номер открытого), `current_flow` (мл/мин, пока заглушка `0`), `total_water_used` (литры накопительно, пока заглушка `0`) |
| `IrrigationCommand` | `MSG_COMMAND` | `target_valve` (0=закрыть всё), `mode` (0=время/1=объём), `duration_sec`, `volume_l` |
| `AckData` | `MSG_ACK` (общий для всех `device_type`, не только irrigation) | `acked_packet_id` (какую команду подтверждаем), `status` (0=принято, 1=отклонено) |

На Хабе разбор `payload` диспетчеризуется **по `device_type`**, а не
только по `msg_type` — см. `handleIrrigationPayload()` в `hub.ino`. Это
специально сделано так, чтобы добавление нового типа устройства
(например, `TYPE_LIGHTING`) не ломало разбор существующих: неизвестный
`device_type` просто логируется как неподдержанный, а не интерпретируется
как irrigation-payload.

### 6.1. Физическое управление клапанами (GPIO)

`active_valve` в `IrrigationTelemetry` теперь отражает реальное состояние
пинов на `flow_node`, а не переменную-заглушку. На месте реального
MOSFET-ключа сейчас светодиоды через резистор, подключённые к:

| Индекс клапана | GPIO | Маркировка NodeMCU/Wemos D1 mini |
|---|---|---|
| 1 | GPIO5 | D1 |
| 2 | GPIO4 | D2 |
| 3 | GPIO14 | D5 |
| 4 | GPIO12 | D6 |

Задаются массивом `valvePins[]` в начале `flow_node.ino` —
при другой распиновке менять только его. Намеренно не задействованы
загрузочные пины ESP8266 (GPIO0/2/15/16) — они влияют на режим старта
платы, и висящий на них светодиод/нагрузка могут мешать загрузке или
прошивке.

`applyValveState(valve)` выставляет все пины явно при каждом вызове
(HIGH на целевом клапане, LOW на остальных), а не полагается на
предыдущее состояние — это исключает ситуацию, когда старый клапан
останется включённым при переключении на другой. Вызывается в трёх местах:
при обработке `MSG_COMMAND`, в `checkWatchdog()` и раз в `setup()` (чтобы всё
гарантированно было выключено сразу после загрузки, до подключения к сети).

### 6.2. Масштабирование: таблица устройств и джиттер

Рассчитано на плановые 30-50 узлов + один ретранслятор.

**Таблица устройств на Хабе** (`devices[MAX_DEVICES]`, `MAX_DEVICES=64` с запасом)
использует LRU-вытеснение: когда все слоты заняты, новое
устройство занимает место того, которое дольше всех молчало
(самое старое `lastSeenTime`), а не первое по порядку — **С одним важным
исключением: установленные (`installed=true`) записи из поиска на
вытеснение исключаются полностью** — см. §11. Без этого
физически заменённый/снятый с эксплуатации узел навсегда занимал бы
слот, и `MAX_DEVICES` со временем значило бы не "сколько узлов работает
одновременно", а "сколько узлов когда-либо подключалось с момента
последней перепрошивки Хаба".

**Джиттер на `flow_node`**: базовые интервалы отправки `MSG_TELEMETRY`/`MSG_CONFIG`
(10 сек / 1 час) случайно сдвигаются в пределах ±2с / ±5мин
соответственно. Без этого все узлы, включившиеся одновременно
(например, после общего отключения питания на участке), годами бы
отсчитывали интервалы синхронно и сталкивались в эфире одновременно.
Сид-значение генератора случайных чисел выводится из MAC-адреса узла
(FNV-1a хэш) — джиттер детерминирован для конкретной платы (удобно при
отладке по логам), но разный между разными узлами.

## 7. Известные пробелы протокола (открытые TODO)

Собрано в одном месте для наглядности — детали и обоснование см. в
комментариях соответствующих файлов.

- **`mode=1` (полив по объёму) не реализован** — на узле нет ни чтения
  датчика потока, ни логики "лить, пока не наберётся N литров". Клапан
  всё равно реально открывается (через GPIO, см. ниже), но без ограничения
  по объёму — то есть как `mode=0` без таймера на закрытие по времени.
- **Нет таймера на `duration_sec`/`volume_l`** — команда открывает
  клапан и держит открытым до следующей команды или срабатывания
  watchdog по тайм-ауту связи — поле `duration_sec` принимается и логируется, но
  никакого собственного таймера на автозакрытие через N секунд ещё нет.
- **`current_flow`/`total_water_used` — заглушки**, всегда `0`. Не
  персистентны (при перезагрузке узла накопленный объём в реальной
  реализации нужно будет хранить в EEPROM/flash, а не в RAM).
- **Нет шифрования/аутентификации** — любое устройство в радиусе
  действия, знающее формат пакета, может отправить `MSG_COMMAND` от
  имени "Хаба". Для дачи в текущем контексте это, вероятно, приемлемый
  риск, но стоит иметь в виду.
- **Канал Wi-Fi зафиксирован константой** (`ESPNOW_CHANNEL` в `GardenProtocol.h`).
  Сейчас это не проблема: Хаб сам задаёт канал через собственную точку
  доступа (см. §10), никакого внешнего роутера нет. Но если впоследствии
  Хаб будет подключаться к домашнему/GSM роутеру вместо своей точки
  доступа (вариан B из §10) - проблема вернётся: канал внешнего
  роутера мы не контролируем, потребуется либо закрепить его канал вручную,
  либо реализовать рассылку актуального канала периферии.
- **Serial- и веб-команды Хаба (`open`/`volume`/`close`) жёстко заточены под
  полив.** Когда появится второй тип устройства (например, освещение),
  им потребуется свой набор команд/полей веб-страницы — общий разбор строки
  (`list`, парсинг `idx`) и каркас веб-страницы можно переиспользовать, специфичные
  команды — нет.
- **Веб-интерфейс без авторизации.** Любой, кто знает пароль от точки
  доступа Хаба, может управлять клапанами через `/api/command` — тот же
  компромисс, что и отсутствие шифрования в ESP-NOW выше.

## 8. Пример последовательности обмена (штатный сценарий)

```
0. Хаб включается (или перезагружается)
   Hub -> ВСЕМ   MSG_CONFIG (broadcast, receiver_mac=FF..FF)   x3 с паузой 1с
   [узлы, увидев это, сбрасывают dedup-счётчик для Хаба, см. §4.3]

1. flow_node включается
   flow_node -> Hub   MSG_CONFIG   {valve_count=4, has_flow_sensor=1}

2. Хаб регистрирует устройство (list -> появляется #0)

3. Оператор в Serial Хаба: open 0 2 15
   Hub -> flow_node   MSG_COMMAND  {target_valve=2, mode=0, duration_sec=15}

4. flow_node принимает, реально открывает клапан 2 (GPIO -> HIGH)
   flow_node -> Hub   MSG_ACK      {acked_packet_id=<id команды>, status=0}

5. Через <=10 сек, очередная телеметрия уже отражает новое состояние
   flow_node -> Hub   MSG_TELEMETRY {active_valve=2, current_flow=0, total_water_used=0}

6. Если за 30 сек (WATCHDOG_TIMEOUT_MS) не было НИКАКОГО валидного
   пакета от Хаба - flow_node сам закрывает клапан:
   [локально, без сети] activeValve = 0, applyValveState(0) -> GPIO в LOW, лог в Serial узла
```

Тот же сценарий с ретранслятором между Хабом и узлом (прямой связи нет)
отличается только тем, что шаги 3 и 4 физически идут через `relay`:
Хаб слышит `relay`, `relay` слышит узел и наоборот; для протокола на
уровне payload это прозрачно — дублирования пакетов при одном
единственном пути распространения не возникает.

## 9. Библиотека `GardenNet`

### 9.1. Обязательный шаг установки

Библиотека физически создана внутри `smart_garden/libraries/GardenNet/`
(ограничение инструмента, которым она сюда записывалась). Чтобы Arduino
IDE увидела её для ЛЮБОГО скетча (не только через File → Open открытый
именно из этой папки), нужно перенести её на уровень выше — в глобальную
папку библиотек скетчбука:

```
mv "C:\Users\<user>\Documents\Arduino\smart_garden\libraries\GardenNet" "C:\Users\<user>\Documents\Arduino\libraries\"
```

(путь и разделители — под Windows; на Linux/macOS аналогично: `mv
~/Arduino/smart_garden/libraries/GardenNet ~/Arduino/libraries/`). После
переноса перезапустите Arduino IDE, чтобы она перечитала список
библиотек.

### 9.2. Что внутри

```
GardenNet/
├── library.properties
└── src/
    ├── GardenProtocol.h   - протокол: UniversalPacket, DeviceType, MsgType,
    │                        Irrigation*/AckData, ESPNOW_CHANNEL, isNewerPacketId()
    ├── GardenNode.h        - класс переиспользуемой логики периферийного узла
    └── GardenNode.cpp
```

**`GardenProtocol.h`** — то же самое, что раньше лежало в `common.h`,
без изменений по содержанию, просто теперь в одном месте.

**`GardenNode`** — класс, инкапсулирующий то, что раньше было бы
продублировано в коде КАЖДОГО периферийного узла: подготовку
заголовка пакета, адресацию (личный MAC + широковещательный), сброс
 dedup по announce Хаба, самую дедупликацию, джиттер интервалов
CONFIG/TELEMETRY, watchdog по таймауту связи, автоматическую отправку
MSG_ACK на команды. `flow_node.ino` уже переведён на использование этого
класса (сократился примерно вдвое) и служит живым примером для будущих
узлов.

Специально НЕ входит в класс:
- **Транспорт** (`esp_now_init`/`esp_now_send`/регистрация recv-колбэка)
  — отличается между ESP8266 и ESP32, поэтому передаётся в класс уже
  готовой функцией `SendFn`, а не вызывается изнутри.
- **Домен устройства** (что конкретно в payload CONFIG/TELEMETRY, что
  делать с командой, что делать при потере связи) — передаётся через
  четыре колбэка (`fillConfig`, `fillTelemetry`, `onCommand`,
  `onWatchdog`), реализуемых в самом скетче.

### 9.3. Как будет выглядеть новый тип узла (например, освещение)

```cpp
#include <ESP8266WiFi.h>
#include <espnow.h>
#include <GardenProtocol.h>
#include <GardenNode.h>

GardenNode node;

bool sendRaw(const uint8_t *data, size_t len) {
    return esp_now_send(broadcastAddress, (uint8_t *) data, len) == 0;
}

void fillConfig(UniversalPacket &pkt) { /* заполнить lighting-паспорт */ }
void fillTelemetry(UniversalPacket &pkt) { /* текущее состояние света */ }
uint8_t onCommand(const UniversalPacket &pkt) { /* включить/выключить */ return 0; }
void onWatchdogTimeout() { /* например, погасить свет при потере связи */ }

void onDataRecv(uint8_t *mac, uint8_t *data, uint8_t len) {
    if (len != sizeof(UniversalPacket)) return;
    UniversalPacket pkt;
    memcpy(&pkt, data, sizeof(pkt));
    node.handleIncoming(pkt);
}

void setup() {
    // ...esp_now_init/register_recv_cb/add_peer как обычно...
    node.begin(TYPE_LIGHTING, myMac, sendRaw);
    node.setCallbacks(fillConfig, fillTelemetry, onCommand, onWatchdogTimeout);
    node.setTiming(10000, 2000, 3600000, 300000, 30000);
    node.sendConfig();
}

void loop() { node.loop(); }
```

Потребуется добавить `TYPE_LIGHTING` и структуры `Lighting*` в
`GardenProtocol.h` (см. §6, union `payload`) и `handleLightingPayload()`
на Хабе — сам класс `GardenNode` менять не придётся.

## 10. Веб-интерфейс Хаба

Хаб может отдавать веб-страницу управления с тем же набором действий,
что и Serial-команды (`list`/`open`/`volume`/`close`), доступную с телефона/ноута
через браузер. Подробности эндпоинтов — `hub/README.md`. Здесь — почему
выбран именно такой способ подключения.

### 10.1. Два варианта сети и почему выбран вариант A

**Вариан A (реализован)** — Хаб поднимает СОБСТВЕННУЮ точку
доступа Wi-Fi (`WiFi.softAP()`, режим `WIFI_AP_STA`). Телефон/ноут
подключается напрямую к сети Хаба.

**Вариан B (не реализован)** — Хаб подключается к внешнему
Wi-Fi (домашний роутер/GSM-модем в режиме точки доступа), телефон
остаётся в обычной сети.

Причина выбора A на этом этапе — двоякая:

1. **Вероятная среда развёртывания.** В поле рядом с грядками может не быть
   домашнего роутера вообще — вместо него может использоваться GSM-модем.
   Вариан A не зависит от внешней сетевой инфраструктуры вообще.
2. **Радиоканал полностью под контролем Хаба.** Раз Хаб сам создаёт точку
   доступа, он же выбирает её канал — можно явно задать тот же
   `ESPNOW_CHANNEL`, что использует периферия. С вариантом B пришлось бы
   решать уже задокументированную в §7 проблему рассинхронизации канала с
   внешним роутером — внешний канал мы не контролируем, а ESP-NOW требует
   совпадения канала у всех участников.

Верифицировано официальными примерами arduino-esp32: ESP-NOW и режим
`WIFI_AP_STA` работают вместе, если канал ESP-NOW совпадает с каналом
точки доступа (задаётся аргументом `channel` в `WiFi.softAP(ssid, password, channel)`).

### 10.2. Компромиссы варианта A

- Телефон/ноут, пока подключён к точке доступа Хаба, обычно теряет
  доступ в интернет — стандартное поведение для отдельной локальной сети,
  не баг конкретно этой реализации.
- Авторизации на самой веб-странице нет — единственный рубеж сейчас —
  пароль Wi-Fi точки доступа (см. `AP_PASSWORD` в `hub.ino`).

### 10.3. API

| Эндпоинт | Метод | Формат | Действие |
|---|---|---|---|
| `/` | GET | — | HTML-страница управления (встроенная в прошивку, `INDEX_HTML` в `WebPage.h`) |
| `/api/devices` | GET | JSON-массив объектов `{idx, mac, type, agoSec, activeValve, installed}` | Снимок таблицы `devices[]` |
| `/api/command` | POST | `application/x-www-form-urlencoded`: `idx, valve, mode, duration, volume` | Вызывает `sendCommand()` напрямую - тот же путь, что и у Serial-команд |
| `/api/install` | POST | `application/x-www-form-urlencoded`: `idx` | Подтвердить устройство (см. §11) |
| `/api/forget` | POST | `application/x-www-form-urlencoded`: `idx` | Удалить устройство из таблицы и NVS (см. §11) |

JSON для `/api/devices` собирается вручную через конкатенацию `String`, без
внешних библиотек вроде ArduinoJson — ответ маленький, дополнительная
зависимость ради этого не оправдана.

Сервер синхронный (встроенный `WebServer.h` из arduino-esp32) — вызов
`server.handleClient()` добавлен в `loop()` рядом с обработкой Serial-команд —
оба входа работают независимо друг от друга.

### 10.4. Кэш телеметрии на Хабе

Для отображения состояния клапана на странице в `KnownDevice` добавлено поле
`lastActiveValve` — обновляется в `handleIrrigationPayload()` при каждой
`MSG_TELEMETRY`. Это единственное поле в таблице устройств, завязанное с
domain-специфичным payload (irrigation) — когда появится второй тип
устройства, ему потребуется своё аналогичное поле или более общий механизм
кэширования последней телеметрии по типам устройств.

## 11. Установка устройств (персистентная, защищённая от вытеснения)

### 11.1. Проблема, которую это решает

Автоматическая регистрация (§6.2) удобна для быстрого старта, но у неё
два свойства, неприемлемых для устройства, физически вкопанного на
участке и остающегося там постоянно:

1. **Любой кандидат может быть вытеснен LRU** при заполнении таблицы —
   нормально для временных "кандидатов", но неприемлемо для уже
   физически установленного и подключённого к клапанам устройства.
2. **Таблица целиком живёт в RAM** и очищается при перезагрузке Хаба —
   даже без LRU, простой перезапуск Xаба обнуляет всё, что было известно.
   Самовосстановление по трафику быстрое (первая же `MSG_TELEMETRY` от
   узла вернёт его в таблицу), но не гарантировано, и до этого момента
   устройство просто "не видно" ни в таблице, ни в веб-интерфейсе.

### 11.2. Схема решения

Таблица устройств стала двухуровневой полем `installed` в `KnownDevice`:

| | Кандидат (`installed=false`) | Установлено (`installed=true`) |
|---|---|---|
| Как появляется | Автоматически, по первому пакету | Явное действие пользователя (веб/Serial) |
| LRU-вытеснение | Подвержен | Исключён из поиска на вытеснение |
| Живёт | Только в RAM | RAM + NVS (переживает перезагрузку) |
| Удаление | Само по LRU или явно (`forget`) | Только явно (`forget`) |

**Переход кандидат → установлено** происходит только через `POST /api/install`
(или Serial `install <idx>`). Обратного автоматического перехода нет —
это сознательно, механизм существует именно для того, чтобы человек
явно подтвердил, что это именно то физическое устройство, которое он хотел
установить — автоматическое "устройство прислало достаточно трафика и стало
постоянным" было бы непредсказуемым и могло бы случайно привязать к
таблице постороннее устройство, оказавшееся в радиусе действия.

### 11.3. Формат хранения в NVS

Используется `Preferences` (обёртка arduino-esp32 над NVS), пространство
имён `smartgarden`, один ключ `installed`, значение — сырой блоб из массива
записей `InstalledDeviceRecord { mac[6], deviceType }` — по 7 байт на устройство
(структура может выравниваться компилятором до 8, не важно — это внутренний
формат Хаба для самого себя, а не протокольная структура как `UniversalPacket`,
кросс-платформенность layout здесь не требуется).

Сохраняются только MAC и тип устройства — минимум, необходимый для повторного
опознавания устройства при следующей загрузке. Оперативные поля
(`lastSeenTime`, `lastActiveValve` и т.п.) не сохраняются и восстанавливаются из
реального трафика после старта, а не из NVS.

Запись в NVS (`saveInstalledDevicesToNVS()`) происходит только по явному
действию пользователя (install/forget), целиком перезаписывая весь
блоб целиком заново (не инкрементально). Эти события редкие (не привязаны
к частоте пакетов, в отличие от, скажем, отправки телеметрии), поэтому
проблемы с износом flash от частых перезаписей не возникает.

`loadInstalledDevicesFromNVS()` вызывается один раз в `setup()`, **до** инициализации
ESP-NOW и начала приёма трафика — чтобы восстановленные установленные устройства
заняли свои слоты (0..count-1) раньше, чем туда смогло бы попасть что-либо
автообнаруженное.

### 11.4. Граничный случай: все слоты заняты установленными

Если все `MAX_DEVICES` слотов заняты установленными устройствами,
`findOrRegisterDevice()` для нового кандидата возвращает `-1` (не
зарегистрирован, но и ничего не вытесняет) вместо вытеснения чего-то.
`onDataRecv()` уже обрабатывает этот случай (`if (idx < 0) return;`), так что
дополнительной обработки не потребовалось — новый кандидат просто останется
невидимым для Хаба, пока какое-то установленное устройство не будет
явно забыто. При плановых 30-50 узлах и `MAX_DEVICES=64` это маловероятный
сценарий, но не невозможный при дальнейшем росте числа установленных устройств.
